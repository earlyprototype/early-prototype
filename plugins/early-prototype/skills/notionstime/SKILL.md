# /notionstime

If this skill has loaded, the user is Thom and the work touches his research programme. This is his personally developed programme context, installed in his Claude account to keep cross-project understanding portable across sessions.

The programme operates across several projects working a shared underlying question through different substrates.

This skill is a folder. Read `README.md` for the programme overview and the project index. Read individual project files in `projects/` as relevant to the current work.

```

├── README.md           (programme overview and project index)

    ├── _template.md    (structure for new project summaries)
```

## The programme

Thom's research operates across multiple projects working a shared underlying question at different scales: *how does shape determine what cognition produces, and how do we design with that honestly?*

Each project approaches this question through a different substrate — weight geometry, methodology, operational context, project state, visual cognition. The projects are not independent; the connections between them are substantive and worth surfacing when relevant.

Full programme map and project links: see `README.md`.

---

## Methodology that runs across projects

This is general working guidance. Specifics live in individual project files.

**Iterative work in declared phases.** Projects move through named phases. Phase boundaries make pause-and-resume tractable.

**Continuity documents that hold canonical state.** JOURNEY_MAP files, working_context documents, README structures that include status, dependencies, and open questions. These are working artefacts, not administrative overhead.

**Hypotheses held provisionally with status markers.** Confidence is named explicitly. Provisional thinking is marked as provisional rather than presented as established.

**Negative results documented with the same weight as supported findings.** The work does not perform success.

**Documentation as cognitive work.** The act of documenting shapes the thinking. The artefacts are the work, not records of work done elsewhere.

**Metacognitive externalisation.** Supervisor sessions, friction logs, or equivalent structures surface patterns the practitioner cannot see from inside their own work.

This is constructionist methodology applied to research. Apply it when contributing to any project in the programme.

## Working across projects

Cross-project connections are often substantive. When a possible intersection appears, surface it to Thom rather than asserting it independently. Some connections are well-established (named in `README.md` and in individual project files); others may be emergent.

The programme's intellectual location — at the intersection of constructionist pedagogy, dynamical systems theory, mechanistic interpretability, post-structuralist philosophy (Deleuze), maker-centred learning, and AI architecture — is unusual. Engage with the breadth.

## Adding new project summaries

When working on a project not yet in `projects/`:

1. Propose adding a summary file to Thom.
2. Wait for explicit clearance before adding. The project may need more development, the framing may not be settled, or its place in the programme may not yet be decided.
3. When clearance is given, use `projects/_template.md` as the structure.
4. Draft the summary and present it for Thom's review before committing.
5. Use Thom's own framing where possible — quote from his README files and direct statements.
6. Update `README.md` to add the project to the index.

## How to use this skill

Read `README.md` first. Identify which project(s) the current work touches. Read those project files. Hold the methodology and cross-project guidance from this file throughout.

When uncertain about a project's status, framing, or place in the programme: ask Thom.
